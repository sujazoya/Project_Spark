# Project Spark

## Display System — Complete Technical Documentation

**System:** `ProjectSpark.Display`
**Engine:** Unity 6
**Rendering:** Unity UI / TextMeshPro / URP-compatible
**Architecture Status:** Complete
**System Role:** Professional electronic-instrument display and presentation layer

---

# 1. System Purpose

The Project Spark Display System provides the presentation layer for electrical measurements, instrument states, ranges, alarms, signal quality, graphs, and measurement statistics.

The Display System is **not the source of electrical truth**.

The source of truth remains the simulation/measurement system.

The Display System receives already-determined values and converts them into a professional instrument-style visual presentation.

```text
Electrical Simulation
        │
        ▼
Measurement / Device State
        │
        ▼
SparkDisplayData
        │
        ▼
SparkAdvancedDisplay
        │
        ├── Primary Value
        ├── Secondary Value
        ├── Tertiary Value
        ├── Unit
        ├── Mode
        ├── Status
        ├── Bar
        ├── Range
        ├── Alarm
        ├── Signal Quality
        ├── Graph
        └── Statistics
```

---

# 2. Design Principles

The system follows these principles:

## 2.1 Simulation Is the Source of Truth

Display animation must never modify electrical simulation values.

For example:

```text
Simulation:
12.48 V

Display:
12.47 V
12.48 V
12.49 V
```

may happen because of visual interpolation or instrument presentation noise.

The simulation value remains:

```text
12.48 V
```

The visual value is presentation only.

# 10. Transition Types

Primary numeric transitions:

```text
Instant
Smooth
Instrument
Rolling
```

### Instant

The display immediately changes to the target value.

### Smooth

The display approaches the target using exponential smoothing.

### Instrument

The display uses smoothing plus optional visual instrument noise.

### Rolling

The display moves from the previous visual value toward the new value over a configured duration.

# 14. Why DisplayData Is Cloned

When:

```csharp
display.SetData(data);
```

is called, the display creates a copy.

Therefore:

```text
External source data
        │
        │ Clone
        ▼
Display-owned state
```

The display cannot accidentally modify the caller's object.

This also allows safe equivalence comparisons.

---

# 15. Data Equivalence

`SparkDisplayData.IsEquivalentTo()` determines whether the visual state has meaningfully changed.

It compares:

* primary
* secondary
* tertiary
* mode
* state
* quality
* bar
* range
* labels
* status
* notification
* signal quality
* graph state

Numerical comparisons use tolerance where appropriate.

---

# 16. Data Tolerance

`SparkAdvancedDisplay.dataTolerance` is a **rendering optimization**.

Example:

```text
12.000000
12.000001
12.000002
```

may be visually equivalent.

The renderer does not need to restart animations for every tiny change.

However:

**Measurement statistics still receive every valid sample.**

This distinction is critical.

---

# 18. Rolling History

`SparkDisplayHistory` stores the most recent samples.

Default capacity:

```text
256
```

The history uses a circular array.

This provides efficient sample insertion without repeatedly shifting the entire collection.

---

# 19. History Statistics

Rolling history provides:

```text
Minimum
Maximum
Average
Latest
```

These statistics are based on the current rolling history.

If capacity is 256, then the statistics represent the latest 256 samples.

---

# 20. Peak Hold

`SparkDisplayPeakHold` is different from rolling maximum.

Example:

```text
Samples:

10
20
30
40
20
10
```

Rolling maximum may become:

```text
20
```

after the old `40` leaves the rolling history.

Peak hold remains:

```text
40
```

until:

```text
ResetStatistics()
```

is called.

---

# 21. Statistics Reset

Calling:

```csharp
ResetStatistics();
```

clears:

```text
Rolling History
Peak Hold
```

It does not clear:

```text
Current Display Data
Graph
Simulation
```

---

# 22. Clear Behavior

Calling:

```csharp

```

It clears:

```text

Mode
Status
Secondary
Tertiary
Unit

Notification
Bar
Range
Alarm
Signal Quality
Graph
```

It does **not** clear measurement statistics.

This distinction is intentional.

# 23. Statistics Data Flow

Every valid primary sample follows:

```text
SparkDisplayData.primary.value
             │
             ▼
SparkDisplayStatisticsTracker.Add()
             │
       ┌─────┴─────┐
       ▼           ▼
    History     Peak Hold
       │           │
       └─────┬─────┘
             ▼
       SparkDisplayStatistics
```

---

# 24. Graph Data Flow

Graph samples are independent of primary statistics.

```text
SparkDisplayData.graphValue
             │
             ▼
SparkDisplayGraph.AddSample()
             │
             ▼
Circular Sample Buffer
             │
             ▼
UI Mesh
```

The graph can therefore represent a signal independently from the primary formatted value.

---

# 25. Graph Capacity

Default:

```text
128 samples
```

The graph uses a circular buffer.

When full:

```text
oldest sample
     ↓
replaced by
     ↓
newest sample
```

This avoids:

```text
RemoveAt(0)
```

and the associated array shifting.

---

# 26. Graph Auto Range

When:

```text
autoRange = true
```

the graph calculates the visible range from its current samples.

Padding is applied using:

```text
autoRangePadding
```

Example:

```text
Minimum sample = 10
Maximum sample = 20

Range = 10

Padding = 10 × 0.05
        = 0.5

Display range:
9.5 → 20.5
```

---

# 27. Manual Graph Range

When:

```text
autoRange = false
```

the graph uses:

```text
minimum
maximum
```

If:

```text
clampInput = true
```

samples are clamped to this range.

When auto-range is enabled, actual samples are retained so the graph can correctly determine its range.

---

# 28. Zero Line

If:

```text
showZeroLine = true
```

and:

```text
currentMinimum < 0
currentMaximum > 0
```

the graph renders a zero reference line.

This is particularly useful for:

* AC signals
* current direction
* signed voltage
* differential signals
* error signals

---

# 29. Graph Rendering

The graph inherits from:

```csharp
UnityEngine.UI.Graphic
```

The graph creates its own mesh through:

```text

```

Each line segment is rendered as a small quad.

This avoids requiring a separate LineRenderer.

# 34. Deadband

Primary renderer deadband is different from display data tolerance.

```text

    → controls state/application updates

    → controls visual convergence
```

This prevents unnecessary micro-movement in the visual display.

# 46. SetData Pipeline

Calling:

```csharp
display.SetData(data);
```

performs:

```text
1. Validate input
2. Clone data
3. Record measurement sample
4. Record graph sample
5. Compare visual state
6. If equivalent → update statistics display only
7. Otherwise → store current data
8. Apply animation configuration
9. Apply visual data
```

This ordering is deliberate.

---

# 47. Why Sampling Happens Before Equivalence

Suppose:

```text
dataTolerance = 0.001
```

and the simulation produces:

```text
1.000
1.0004
1.0007
1.0010
```

The visual state may not need to update for every sample.

However, those are still real measurement samples.

Therefore:

```text
RecordMeasurementSample()
```

runs before:

```text
IsEquivalentTo()
```

This is one of the most important rules in the system.

# 61. Performance Characteristics

The system is designed to avoid unnecessary work.

### Display equivalence

Equivalent visual states do not restart all visual renderers.

### Statistics

History insertion is constant-time.

### Graph

Graph samples use a circular buffer.

### Graph mesh

The mesh is marked dirty only when graph data/configuration changes.

### UI animation

Animations update using lightweight interpolation.

### No global managers

There is no singleton display manager.

---

# 62. Threading

The Display System is designed for normal Unity main-thread use.

Unity UI objects such as:

```text
TMP_Text
Image
CanvasGroup
Graphic
```

must remain on the Unity main thread.

The underlying simulation may use its own execution model, but display application should occur on the Unity thread.

---

# 63. Error Handling

Invalid numerical values are rejected:

```text
NaN
Infinity
```

Invalid primary display values result in:

```text
----
```

Invalid graph samples are ignored.

Invalid statistics samples are ignored.

The system therefore avoids propagating invalid numerical state into UI calculations.

---

# 64. Current Data vs Statistics

These are deliberately different.

```text
CurrentData
    = latest display state

Statistics
    = measurement history
```

Therefore:

```text
CurrentData.primary.value
```

does not necessarily equal:

```text
Statistics.average
```

and that is expected.

---

# 65. Current Data vs Graph

Likewise:

```text
CurrentData.primary
```

and:

```text
Graph samples
```

are independent.

The graph can represent a dedicated signal:

```text
graphValue
```

while the primary display represents:

```text
primary.value
```

---

# 66. Reset Rules

| Operation              | Display           | Graph    | Statistics | Peak     |
| ---------------------- | ----------------- | -------- | ---------- | -------- |
| `SetData()`            | Update            | Add      | Add        | Add      |
| Equivalent `SetData()` | Usually unchanged | Add      | Add        | Add      |
| `Clear()`              | Clear             | Clear    | Preserve   | Preserve |
| `ResetStatistics()`    | Preserve          | Preserve | Clear      | Clear    |
| `SetPowered(false)`    | Hide              | Preserve | Preserve   | Preserve |
| `SetPowered(true)`     | Restore           | Preserve | Preserve   | Preserve |

This is the intended lifecycle.

# 79. Architectural Boundary

The correct dependency direction is:

```text
Simulation
    ↓
Measurement
    ↓
Display Data
    ↓
Display
    ↓
UI
```

Not:

```text
UI
    ↓
Simulation
```

The UI is therefore a consumer of state.

# 80. Why There Is No Display Manager

A global manager is unnecessary.

Each physical display can own:

```text
SparkAdvancedDisplay
```

and receive its own data.

This allows:

```text
Multimeter
Oscilloscope
Power Supply
Battery Display
PLC Display
Motor Controller
Temperature Display
Frequency Counter
```

to use the same foundation without global coordination.

---

# 81. Multiple Displays

Multiple instruments can independently receive different data.

Example:

```text

    → 12.4 V

Current Display
    → 0.52 A

    → 6.45 W

    → 60.0 Hz
```

Each instance maintains its own:

```text
history
statistics
peak
graph

```

# 82. Determinism

The measurement data itself remains deterministic if supplied by a deterministic source.

Visual animation is intentionally time-dependent.

Therefore:

```text
Simulation state
    = deterministic source of truth

Display animation
    = presentation layer
```

Instrument noise is explicitly presentation-only.

# 83. Extending the System

When adding a new display feature, first determine whether it is:

```text
Data
Formatting
Statistics
Animation
Rendering
Orchestration
```

Add functionality to the existing appropriate class when possible.

Do not create a new class merely to wrap one field or method.

---

# 84. Adding a New Measurement Unit

To add a new canonical unit:

1. Add it to `SparkDisplayUnit`.
2. Add its text mapping to `SparkDisplayFormatter.UnitText()`.
3. Verify formatter behavior.
4. Add tests.
5. Do not create duplicate unit enums.

---

# 85. Adding a New Display State

To add a new state:

1. Add the enum value.
2. Add its default status text.
3. Decide whether it is a warning-animation state.
4. Update the status renderer.
5. Update tests.

The simulation/measurement source remains responsible for deciding when that state occurs.

---

# 86. Adding a New Transition

A new transition belongs in:

```text
SparkDisplayValueTransition
SparkDisplayValueRenderer
```

It should remain a visual behavior.

It must never alter the measurement value.

---

# 87. Adding a New Graph Feature

Graph-specific functionality belongs in:

```text
SparkDisplayGraph
```

Do not move graph sample storage into `SparkAdvancedDisplay`.

The orchestrator only forwards data.

---

# 88. Adding a New Statistic

If a statistic depends on measurement history:

```text
SparkDisplayStatisticsTracker
```

should own its calculation.

If it requires a fundamentally different history model, introduce that only when an actual requirement exists.

---

# 89. Production Rules

The following rules should remain locked:

```text
1. Simulation state is authoritative.

2. Display animation is presentation only.

3. Statistics receive every valid measurement sample.

4. Graph receives every accepted graph sample.

5. Rendering tolerance must not discard measurement history.

6. Clear() does not reset statistics.

7. ResetStatistics() resets statistics and peak hold.

8. Formatting belongs to SparkDisplayFormatter.

9. Graph owns graph samples.

10. Renderers do not calculate electrical behavior.

11. AdvancedDisplay orchestrates; it does not simulate.

12. No global DisplayManager is required.

13. No Event Bus is required.

14. No Singleton is required.

15. No reflection is required.

16. No service locator is required.

17. No unnecessary abstraction layer should be added.
```
